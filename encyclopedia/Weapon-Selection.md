# Weapon Selection — `TechnoClass::WhatWeaponShouldIUse` (a.k.a. `SelectWeapon`)

The function that answers "which of my weapons do I use against *that*". Called
from targeting, cursor rendering, threat evaluation and firing, so it is one of
the hottest and most contested functions in the game.

Vanilla body spans roughly `0x6F3330`–`0x6F3813`.

---

### `0x6F3330` — entry  ⚠ registry previously said Antares owns this. It does NOT.

**Framework names**

| Framework | Function name | Stolen | Status |
|---|---|---|---|
| Antares | `TechnoClass_SelectWeapon` | 0x5 | **commented out — not compiled** |
| Ares | `TechnoClass_SelectWeapon` | 0x5 | unverified, source not to hand |

**The correction.** `registry/hooks.csv` listed `0x6F3330` as a live Antares
release hook. It is not. In `src/Ext/Techno/Hooks.cpp` the `DEFINE_HOOK` sits at
line 440 inside a block comment opened at line 439 and closed at line 608 — the
hook *and* the whole `SelectWeaponAgainst` implementation are commented out.
Only a stale declaration survives, in `src/Ext/Techno/Body.h:285`; nothing calls
it, which is why the dead declaration never becomes a link error.

The registry is generated by scanning source for `DEFINE_HOOK`, and **that
scanner cannot see C comments**. Any hook a framework has commented out still
appears as live. This was the first confirmed false positive; treat a registry
row as a *lead*, and confirm against the source before conceding an address.

Rows have been re-channelled to `COMMENTED-OUT` (Antares, verified) and
`UNVERIFIED` (Ares, not checked) rather than deleted, so the claim is not simply
lost.

**Why it matters.** A false "occupied" reading makes you concede an address that
is actually free, and the whole point of
[Don't concede framework-owned hooks](../README.md) is that conceding is usually
the wrong instinct. Here the entry appears to be genuinely available.

**Overlap note if you do take it.** A 5-byte hook at `0x6F3330` covers
`0x6F3330`–`0x6F3334`. Phobos' nearest hook is `0x6F3339` (size 0x8), so the two
do not overlap — but the margin is 4 bytes, so re-check before changing size.

## Wrapping it safely: the four vtable slots  ✅ verified in use

`SelectWeapon` is virtual (`YRpp/TechnoClass.h:227`) and `0x6F3330` is referenced
by exactly four `.rdata` vtable slots, one per TechnoClass subclass:

| slot | notes |
|---|---|
| `0x7E2588` | |
| `0x7E41A0` | |
| `0x7E8F78` | |
| `0x7F4C44` | |

All four are unclaimed by Phobos, Antares and the registry. They are confirmed
real vtable entries rather than raw bytes equal to `0x6F3330`: every neighbouring
word at each address is a valid `.text` pointer, and all four are followed by the
same next virtual (`0x6F3820`). `AircraftClass::AbsVTable` is `0x7E22A4`.

Replacing these slots is the **only** safe way to influence weapon choice without
disabling somebody else's work: the wrapper calls the original, so all nine
Phobos and two Antares in-body hooks still run and decide, and you adjust their
answer afterwards.

### ⚠ The wrapper MUST be `__fastcall` with a dummy EDX parameter

A vtable slot is invoked as `__thiscall`: `this` in ECX, arguments on the stack,
callee cleans. MSVC will not accept `__thiscall` on a free function, so:

```cpp
using SelectWeaponFunc = int(__fastcall*)(TechnoClass*, void*, AbstractClass*);

int __fastcall Wrapper(TechnoClass* pThis, void* /*edx*/, AbstractClass* pTarget)
{
    const auto original = reinterpret_cast<SelectWeaponFunc>(0x6F3330);
    const int chosen = original(pThis, nullptr, pTarget);
    ...
}
```

Declaring it `__stdcall(pThis, pTarget)` instead fails twice, silently: `this` is
read off the stack (so the first parameter receives the first real *argument*),
and a two-parameter `__stdcall` callee pops 8 bytes where the caller pushed 4 —
**four bytes of stack imbalance per call**. On a function this hot the return
address is destroyed almost immediately.

**Symptom to recognise:** `C0000005` with **EIP inside `.rdata`** (observed:
`0x007FA9A0`) — the CPU executing data, which means smashed control flow rather
than a null dereference. Map EIP against the section table (`.text` `0x401000`,
`.rdata` `0x7E1000`, `.data` `0x812000`) before theorising about the feature that
appeared to trigger it; in the observed case a paradrop was blamed, but it was
merely the first event that spawned enough objects to call the wrapper.

**Confirmed via.** In-game crash and its `except.txt`; PE section mapping of the
faulting EIP; neighbour analysis of all four slots in `gamemd.exe`; fixed build
re-deployed.

## Second occurrence, and the misdiagnosis it invites  ✅ re-confirmed 2026-09-11

The `__stdcall` wrapper bug recurred and was re-diagnosed from scratch. Recording
it because the *wrong* answer is very attractive and cost a full analysis pass.

**The evidence.** Two `C0000005 at 007FA9A0`, 16:33 and 18:42. The fix commit
(`SuperWeaponExt c76b367`, "the SelectWeapon vtable wrapper used the wrong
calling convention") landed 18:45 and the rebuilt DLL was deployed 19:49. No
crash after. Section table of the running `gamemd-spawn.exe` confirms
`.text` = `0x401000`–`0x7E038D`, `.rdata` = `0x7E1000`–`0x811074`, so
`0x7FA9A0` is **`.rdata`** — EIP executing data.

**The trap.** `0x7FA9A0` looks like it implicates whoever *calls* `SelectWeapon`,
and a search will find callers passing a target pointer straight through. That
reasoning is wrong on mechanism: a bad pointer handed to `SelectWeapon` faults
**inside** it, at `0x6F33xx` in `.text`. Only a stack-imbalanced wrapper produces
an EIP in `.rdata`. **Map EIP to a section before naming a suspect** — it
discriminates "bad data" from "smashed control flow" in one step, and the two
have disjoint suspect lists.

**The second trap: simultaneous redeploys.** Eight DLLs were redeployed in the
same window. "Crashes stopped after X was deployed" identifies nothing when X was
one of eight; the attribution landed on an unrelated DLL whose commit message
happened to mention the same subsystem. Prefer a commit that *names the
mechanism* over one that merely correlates in time.

**Also worth knowing:** an armed building reproduces this on demand, because an
armed building is a target, so `SelectWeapon` gets dispatched at all. Removing
the weapon or moving it to another building tracks the crash exactly — which
looks like evidence for a targeting-logic theory but is really just "does the
broken wrapper get invoked".

## Data-side: `Primary=` is dead on any type that defines `WeaponCount`

Not a hook — a rules-data fact that matters to anyone *writing* weapons through
the INI, and one that fails in the most misleading way possible.

A TechnoType with `WeaponCount=N` answers from its **`Weapon1`..`WeaponN`**
list. Its `Primary=` / `Secondary=` are simply not consulted. Two shapes:

* **`Gunner=yes`** — the slot is chosen by **passenger**. The Allied IFV (`FV`)
  is `Gunner=yes`, `WeaponCount=17`, `Weapon1=HoverMissile ;Normal`. `Weapon1`
  is therefore the *empty transport* weapon, and the rest map to passenger type.
* **Multi-turret** — the slot is chosen by turret/range. The Prism Tank (`SREF`)
  is `WeaponCount=1` with `Weapon1=Comet`, and ships with its `Primary=` line
  **commented out in vanilla** — a good tell that the key is inert there.

**Why this wastes an afternoon.** Writing `[FV] Primary=Comet` succeeds. The INI
accepts it, a tool that logs its own writes reports a clean
`FV.Primary: 'HoverMissile' -> 'Comet'`, and the unit keeps firing missiles. The
log says the change landed — and it did land; it is just never read. A silent
no-op that *reports success* is worse than an outright failure, so a tool writing
weapon keys should check the target for `WeaponCount` and say so.

Note `Primary=` is usually still *present* on these types (the IFV has
`Primary=HoverMissile`), so "the key exists in the section" is not evidence that
it is used. Check `WeaponCount`, not `Primary`.

## `0x70E140` — `TechnoClass::GetWeapon(int)`, and the thread it may run on

The accessor that takes the **instance** in `ECX`, not the type. That is the
whole reason weapons can be made to vary per unit while `Cost` and `Armor`
cannot: those are only ever asked of the shared `TechnoTypeClass`.

33 instructions, and in a RELEASE-channel build nothing in Phobos/Antares hooks
it. Returning a different weapon needs a flow-replacing jump, and the epilogue
pops first, so hook the **entry**: nothing is pushed yet, `ESP` already points
at the return address, and `0x70E151` is a bare `ret 4`.

Elite selection happens off the instance too —
`Veterancy.IsElite() ? EliteWeapon[i] : Weapon[i]`, a hard pick with no fallback
between the arrays (see the elite section above).

### ⚠ It is in `CanAutoTargetObject`'s call tree, so it can leave the game thread

`0x70E140` sits in the **first-pass call tree of `TechnoClass::CanAutoTargetObject`
(`0x6F7CA0`)**. That matters because a framework may move target selection onto
worker threads: PerfExt's "lane 3" parallelises `FootClass::GreatestThreat`'s
candidate loop, and every candidate's `CanAutoTargetObject` then runs off the
game thread. Anything you hook at `0x70E140` runs there too.

`UnitClass::GetFireError` (`0x740FD0`, 306 instructions) is in the same pass-1
tree, reached through the `UnitClass` vtable slot `0x7F6030 + 0x3C0` rather than
by a direct call, and Phobos wraps it first.

**Consequences for a hook at either address.** Keep it read-only, or make its
state thread-local or locked. Specifically:

* A `static` log-once flag or `std::unordered_set` probe is a data race. It
  *looks* harmless because it only writes once — but "once" is decided by
  several threads at the same time, and `Debug::Log` formats into a shared
  buffer besides.
* State written on the **game thread** and read here is a different question,
  and the answer depends on the framework's scheduling rather than on your code.
  Under a fork-join design — the game thread enters the pool from inside one
  `GreatestThreat` call, takes a share of the jobs, and leaves only when the
  done counter says all are finished, running no game logic in between — a
  per-unit map written from `TechnoClass::Update` **cannot** be written while a
  worker reads it, and concurrent reads of an `unordered_map` are safe. Adding a
  lock for that case is not free: a shared SRW acquire is an interlocked write
  to one lock word, so N workers bounce that cache line in the game's hottest
  loop. **Check the framework's scheduling before guarding.**

**Confirmed via.** The static call tree in PerfExt's own audit of a clean
`gamemd.exe` (`PerfExt/docs/lane3-audit-gamemd.md`, rows `0x70e140` and
`0x740fd0`, both pass 1). ⚠ **This is static reachability, not an observed
call.** A "GetWeapon hook reached" line from a live game does *not* establish
that the parallel phase reached it, because `GetWeapon` has many callers — a
distinction the PerfExt session raised against its own earlier wording, and the
one worth preserving if this page is ever used as evidence. Call-site counts for
either address are **not** recorded; cite the call tree instead of inventing
them.

**The fork-join half IS corroborated in game**, and it is worth separating from
the reachability claim above. A 300-second stress match under heavy paradrop
load, with an extension hooking `0x70E140` and `0x740FD0` and keeping no lock on
the per-unit maps its game thread writes, logged **57,352 candidate walks all
forked to 4 workers, 61,973,735 target checks, 0 mismatches, 0 worker
mismatches, 0 redos and no crash** (PerfExt `docs/lane3-plan.md` §20, commit
`d6a7a1e`, 2026-11-09). The framework re-ran stock `CanAutoTargetObject` at
serve time and compared.

Read that for what it is: strong evidence that the fork-join ordering holds and
that unlocked reads are correct under it. It is **not** evidence about
reachability, and a mismatch count cannot rule out a rare
use-after-rehash — it compares results, not memory safety. The reason no such
race exists here is the scheduling argument, not the zero.

### The real rule: the weapon declaration must be COMPLETE on the type

**CORRECTED 2026-09-24.** An earlier revision of this section claimed
"`TurretCount>1` alone kills `Primary=`" and marked it A/B verified. The A/B was
real, but that mechanism was the wrong attribution and it only explained one of
two failures. The measured cause is narrower and more useful:

> **`WeaponN` is only read when `WeaponCount` covers it, and a type's weapon
> declaration is NOT delivered by `$Inherits`.**

**CORRECTED AGAIN 2026-11-02.** The `WeaponCount` half of that is the wrong way
round, and the turret question below is now isolated. See
[What engages the list](#what-engages-the-list-isolated-2026-11-02).

Evidence, from synthesised types whose sections were dumped back key by key so
the write itself was never in doubt (TraitExt, 2026-09-23/24):

| Section as written | Parsed result |
|---|---|
| `$Inherits=FV` + `Weapon1=Comet` (base `FV` is `WeaponCount=17`) | `WeaponCount=0`, **all 18 slots null** |
| `$Inherits=MTNK` + `TurretCount=4` + `Primary=Comet` | `WeaponCount=0`, **all 18 slots null** — not even the parent's `105mm` |
| same section, `Primary=Comet` → `WeaponCount=1` + `Weapon1=Comet` | fires |

The first row is the decisive one. `Weapon1=Comet` was a **literal key on the
section**, and it was still ignored — because the child inherited no
`WeaponCount`, so slot 1 was outside the declared range. `$Inherits` supplies
individual keys lazily on lookup, but the engine reads the weapon list by
*counting*, so a child that does not restate `WeaponCount` has an empty list no
matter what `WeaponN` keys it carries.

That also explains the `Primary=` row without appealing to turrets: with
`WeaponCount=0` **and** a multi-turret mapping engaged, neither path yields a
weapon.

### What engages the list (isolated 2026-11-02)

The paragraph that used to sit here said the `TurretCount>1` question was
"never isolated". It is isolated now, and the answer is the opposite of what
`WeaponCount` being named in the rule above implies:

> **`TurretCount>1`, `Gunner=yes` or `IsGattling=yes` engages the `WeaponN`
> list. `WeaponCount` only BOUNDS it — on its own it engages nothing.**

Four synthesised types from one match, dumped from the live objects at
`GetWeapon` time (TraitExt, 2026-11-02):

| type | `WeaponCount` | `TurretCount` | key written | parsed |
|---|---|---|---|---|
| `SREF$C0` | 1 | 0 | `Weapon1=105mm` | **all 18 slots null** |
| base `SREF` | 1 | 4 | `Weapon1=Comet` | `Weapon[0]=Comet` |
| `MGTK$C2` | 0 | 0 | `Primary=Comet` | `Weapon[0]=Comet` |
| `BFRT$C1` | 0 | 0 | `Primary=105mm` | `Weapon[0]=105mm` |

Rows 1 and 2 are the isolation: same `WeaponCount`, same key spelling, and only
the turret count differs. Rows 3 and 4 kill the converse reading — that
`WeaponCount=0` suppresses `Primary=` — which an earlier revision of this page
inferred from `MTNK$C0`. That case had `TurretCount=4`, so the turret was doing
the work and the count was never the variable.

**Gattling types enter through neither.** Vanilla `[YTNK]` is `TurretCount=1`
with `WeaponCount=6` and `Weapon1..6`, so `IsGattling=yes` is its only way into
the list. A predicate written as "turret count or gunner" silently mistranslates
every Gattling type.

**Why it matters when you synthesise a type.** The selector is a property of the
type you *end up with*, not the one you copied from. A clone that borrows
another unit's art drops the turret family to keep the voxel coherent — and
drops the engagement with it, so a weapon key copied across in `WeaponN` form
becomes unreadable. Translate the key into the form the finished type is read
through (`Weapon1` ↔ `Primary`, `Weapon2` ↔ `Secondary`) rather than trusting
the spelling the author chose. Slots 3 and up have no `Primary`-style spelling,
so a two-slot type cannot express them at all.

Still **unmeasured**: whether a `WeaponCount>0` left on an otherwise
`Primary`-style type suppresses `Primary=`. `SREF$C0` is not evidence either
way — it carried no `Primary` key at all. Zero the count when you de-engage the
list and the question does not arise.

### ⚠ Elite weapons are a PARALLEL array, not a fallback (2026-11-02)

`TechnoTypeClass::GetWeapon(index, elite)` is a hard pick —
`elite ? EliteWeapon[index] : Weapon[index]` (`YRpp/TechnoTypeClass.h:164-173`)
— and `elite` is `TechnoClass::Veterancy.IsElite()`, i.e. `Veterancy >= 2.0f`
(`YRpp/TechnoClass.h:96-98`). There is no fallback from a null elite slot to the
base-rank one at this level; the *callers* fall back to the primary, which is a
different thing.

Two consequences for anything that writes or repoints a type:

1. **A type that declares only `Primary=` is invisible to an elite unit.** This
   is not an edge case: an Academy (`Veterancy-Academy.md`) makes units elite
   **at build time**, so on such a mod the elite array is the *only* one ever
   read. A feature tested on a rookie unit and shipped can be inert for every
   unit the player actually owns.
2. **Copying a base type's section carries its elite guns, which then beat
   yours.** Observed, with the override written and parsed correctly and the
   unit still firing the original:

   ```
   MGTK$C2: Weapon[0]=Comet        EliteWeapon[0]=(null)
            Weapon[1]=HoverMissile EliteWeapon[1]=MirageGunE   <- base's, wins
   ```

   Vanilla `[MGTK]` declares `EliteSecondary=MirageGunE`, so a literal section
   copy hands the clone an elite gun the author never asked for.

**What to do.** Mirror every weapon key you write into its elite spelling
(`Primary`→`ElitePrimary`, `Secondary`→`EliteSecondary`, `WeaponN`→`EliteWeaponN`)
unless the author spelled the elite form out themselves. Decide that on the
*translated* key, or `Weapon1=` and `EliteWeapon1=` race each other into
`Primary=`/`ElitePrimary=` in whatever order the entries happen to be in.

**If you hook `GetWeapon` and return a weapon**, returning "no opinion" on an
empty slot is not neutral: the engine then applies its own primary fallback to
the **real** type, so your variant's gun loses to the original. Answer from your
own arrays instead — base rank when the elite slot is empty, and your primary
when the asked-for slot is empty on the real type too. Not when the real slot is
*populated*: that is the `Gunner` passenger case, and it belongs to vanilla.

**Confirmed via.** In-game, three units in one match, `elite=1` logged on all
three while each kept its original weapon and (where the trait set one) wore the
variant's art — art and weapons travel different paths, so art changing is not
evidence the weapon did. Fix built and **not yet re-tested in game** at the time
of writing.

**The practical rule.** A partial weapon declaration is not a smaller version of
the base — it is a broken type, and it reads in game as a unit that simply never
fires. If you synthesise or edit a type that touches weapons, copy the base's
**whole** declaration (`WeaponCount`, `Gunner`, `Primary`/`Secondary`, `Elite*`,
`Weapon1..18`, `EliteWeapon1..18`) and overwrite individual slots from there;
and raise `WeaponCount` to cover the highest slot you declare, or that slot is
silently never read. For a `Gunner` unit this is also what keeps the passenger
slots working instead of emptying the list.

**Confirmed via.** Vanilla `rulesmd.ini` `[FV]` (`Gunner=yes`, `WeaponCount=17`,
`Weapon1`..`Weapon17`) and `[SREF]` (`WeaponCount=1`, `Weapon1=Comet`, `Primary`
commented out).

**A/B VERIFIED IN-GAME** (TraitExt, 2026-09-19), same unit, same build, same
mechanism — only the key changed:

* `FV.Primary: 'HoverMissile' -> 'Comet'` — logged clean across several
  matches; the IFV kept firing missiles.
* `FV.Weapon1: 'HoverMissile' -> '105mm'` — the empty IFV fired a cannon.

So `Weapon1` is the **empty-transport** slot (vanilla comments it `;Normal`),
and `Primary=` is genuinely never consulted on a `Gunner=yes` type. The negative
half of that A/B is the load-bearing part: it is the case that *looks* like it
worked.
