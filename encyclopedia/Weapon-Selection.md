# Weapon Selection — `TechnoClass::WhatWeaponShouldIUse` (a.k.a. `SelectWeapon`)

The function that answers "which of my weapons do I use against *that*". Called
from targeting, cursor rendering, threat evaluation and firing, so it is one of
the hottest and most contested functions in the game.

Vanilla body spans roughly `0x6F3330`–`0x6F3813`.

---

### `0x6F3330` — entry  ⚠ registry previously said Antares owns this. It does NOT.

**Framework names**

| Framework | Function name | Stolen | Status |
|---|---|---|---|
| Antares | `TechnoClass_SelectWeapon` | 0x5 | **commented out — not compiled** |
| Ares | `TechnoClass_SelectWeapon` | 0x5 | unverified, source not to hand |

**The correction.** `registry/hooks.csv` listed `0x6F3330` as a live Antares
release hook. It is not. In `src/Ext/Techno/Hooks.cpp` the `DEFINE_HOOK` sits at
line 440 inside a block comment opened at line 439 and closed at line 608 — the
hook *and* the whole `SelectWeaponAgainst` implementation are commented out.
Only a stale declaration survives, in `src/Ext/Techno/Body.h:285`; nothing calls
it, which is why the dead declaration never becomes a link error.

The registry is generated by scanning source for `DEFINE_HOOK`, and **that
scanner cannot see C comments**. Any hook a framework has commented out still
appears as live. This was the first confirmed false positive; treat a registry
row as a *lead*, and confirm against the source before conceding an address.

Rows have been re-channelled to `COMMENTED-OUT` (Antares, verified) and
`UNVERIFIED` (Ares, not checked) rather than deleted, so the claim is not simply
lost.

**Why it matters.** A false "occupied" reading makes you concede an address that
is actually free, and the whole point of
[Don't concede framework-owned hooks](../README.md) is that conceding is usually
the wrong instinct. Here the entry appears to be genuinely available.

**Overlap note if you do take it.** A 5-byte hook at `0x6F3330` covers
`0x6F3330`–`0x6F3334`. Phobos' nearest hook is `0x6F3339` (size 0x8), so the two
do not overlap — but the margin is 4 bytes, so re-check before changing size.

### Phobos' occupancy of the same function

Phobos does not take the entry; it wedges into decision points inside the body.
All from `src/Ext/Techno/Hooks.Firing.cpp` unless noted.

| Address | Function | Stolen |
|---|---|---|
| `0x6F3339` | `..._Interceptor` | 0x8 |
| `0x6F3360` | `..._MultiWeapon` | 0x6 |
| `0x6F33CD` | `..._ForceFire` | 0x6 |
| `0x6F3428` | `..._ForceWeapon` | 0x6 |
| `0x6F3432` | `..._Gattling` | 0xA |
| `0x6F348F` | `..._Airstrike` (Hooks.Airstrike.cpp) | 0x7 |
| `0x6F3528` | `..._IsLocomotor` | 0x6 |
| `0x6F36DB` | `..._WhatWeaponShouldIUse` | 0x8 |
| `0x6F37EB` | `..._AntiAir` | 0x6 |

Antares additionally holds `0x6F3410` (`_NoAmmoWeapon`, 0x5) and `0x6F36E3`
(`_Verses`, 0x5, `Ext/WarheadType/Hooks.Verses.cpp`).

⚠ `0x6F36DB` (Phobos, 0x8 → covers `0x6F36DB`–`0x6F36E2`) sits immediately before
Antares' `0x6F36E3`. They abut exactly and do not overlap, which is worth knowing
before adding anything in that neighbourhood — one byte of drift either way and
the two would corrupt each other's stubs.

**Confirmed via.** Antares source at the cited line numbers (comment block
boundaries checked explicitly); Phobos `develop` source; the registry, whose
error prompted this page.
